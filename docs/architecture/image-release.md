# Image publication

Status: input provenance, operator journals and controller through a stopped snapshot are implemented; verifier and retained publication integration remain open. Local sanitation and clone boot are verified. Provider publication and production consumption are not enabled.

An operator build owns its temporary machines, access resources and snapshot. Customer allocations retain their existing journal and budget rules. Every external mutation has a durable intent; a lost response requires reconciliation before another create. The build record remains useful even when credentials, SSH access or the operator process disappear.

## Inputs and release identity

`build:guest` stages a complete public input tree. Its sorted inventory hashes the executable bundle, installer, service units, SSH and sudo policy, pinned downloaded artifacts, artifact metadata and public trust. It excludes derived `image.json`, `image-inputs.json` and `SHA256SUMS` to avoid a hash cycle. Manifest format 2 includes the inventory digest. Its version changes when any public input changes. There are no deployed format 1 guests requiring compatibility.

The build publishes a directory named by the manifest digest and a separate current-build pointer. Consumers capture the digest once. They validate the complete tree against that digest before use; later builds cannot replace their selected directory. Regular-file, path, size, duplicate and checksum checks reject unsafe or incomplete inputs. Publication makes files read-only; a same-owner process can still change permissions, so digest verification remains required. The controller captures the transfer-checksum digest after full validation, then sends its own shell preflight over authenticated management access. Base OS checksum tools validate that digest, every listed file and the absence of extra files or symlinks before any uploaded installer, Node or guestctl executes. The staged verifier is a second consistency check, not the initial trust source. This is provenance of admitted inputs, not a claim of bit-reproducible Ubuntu packages or independent attestation of a hostile builder.

The authenticated chain is inputs → manifest → sanitation receipt → stopped source/snapshot observation → fresh verification boot → signed release. A release carries the full manifest and provider snapshot identity; `GuestImage` is derived from those fields, avoiding competing copies. Signed metadata includes the artifact pins, sanitation source server, observed source shutdown time and a different verification server. Cryptographic validation checks these assertions for consistency; the future provider journal must prove current ownership and that the verifier actually booted the recorded snapshot. An Ed25519 release key is separate from fleet certificate authorities. Consumers verify signature, key validity and revocation, retention, provider ownership and image availability. A deleted verification-only snapshot produces audit evidence but cannot become a production release.

## Operator path

The operator command `pnpm image:build` implements `prepare <config.json>`, `admit <config.json>`, `inspect <build-id>` and `cancel <build-id>`. Preparation validates local input bytes and publishes independent SSH management/host keys in owner-only local directories, returning only the public admission configuration. It needs no DB or provider token. Fresh admission requires the matching key store, reads current pricing and creates no cloud resource. Cancel records a full build-abort intent. The provider runner, automatic advancement and successful retained-release cleanup are not exposed yet. Admission records one exact provider offer, immutable input digest, explicit management address, build deadline, storage ceiling and retention.

The future `advance` command prepares access, creates one builder, copies verified inputs, installs, sanitizes, confirms shutdown, snapshots, verifies one fresh boot, signs a retained release and cleans temporary resources. The runner executes one planned step at a time. Re-entry reads persisted evidence instead of assuming that a previous process reached its next line.

The per-build SSH management key and initial host key are generated locally. Only public keys and secret references enter SQL. The executor materializes cloud-init with the disposable host private key for the exact prepared server attempt. The first SSH connection pins the known public key before upload. It uses isolated credentials, `-F /dev/null`, `IdentitiesOnly=yes` and `IdentityAgent=none`. Sanitation erases this temporary access. Provider tokens and fleet private keys never enter a builder.

The implemented access store verifies directory ownership, file modes, symlinks and private/public correspondence. Atomic publication preserves the first identity across concurrent preparation and restarts. Recovery binds the keys to the admitted build UUID, input digest, management address and secret reference. The prepared-effect renderer checks confirmed dependencies and the exact active command, then rechecks cancellation and deadline after key recovery. Its cloud-init key map supplies the builder host pair. Customer boot uses an explicit empty map because guestctl owns its host identity. An empty `ssh_genkeytypes` list is invalid in current cloud-init. See the [cloud-init SSH module](https://docs.cloud-init.io/en/latest/reference/modules.html#ssh).

The native builder transport exposes inspect, upload, install and sanitize. Each privileged command first checks Ubuntu/architecture, completed cloud-init and the exact root-owned boot identity. SFTP transfers only verified inventory files. The controller's transfer preflight runs before an atomic root-owned installation-start marker is linked into place, and again before executing uploaded code. Only the request that creates that link runs the installer. Retries recover a completed receipt or return `started`; this state does not say whether a disconnected process is still running. A partial installation requires disposal or explicit recovery. `image-builder-work.ts` now persists those phases under the same build lock as provider effects and cleanup. It rechecks the owned server, assigned IP, admission and deadline before using local credentials.

Sanitation removes builder privileges, install state, boot record and keys. Once access has been erased, a lost receipt cannot authorize publication. Local private keys remain available for uncertain resource recovery; terminal cleanup must delete them idempotently only after the builder and temporary access resources are authoritatively absent. The full-abort controller now removes operator keys after SQL records every provider resource absent and no pending effects. It atomically renames the exact owner-only key directory before unlinking known files, so a process restart can finish partial removal. Wrong admission metadata, symlinked directories and unexpected files fail explicitly; another build's directory is never recursively deleted. A filesystem failure after SQL cleanup is retried on the next controller pass.

The builder journal binds one confirmed create effect and server to monotonic `installing → installed → sanitizing → sanitized` progress. SQL validates exact JSON shapes and immutable installation receipts against admission. Installation intent is saved before SSH; a lost completed response is recovered by inspecting the guest receipt, without another upload or installer execution. An interrupted sanitation intent or unknown sanitation response requests full cleanup because the guest may already have erased access. Completion evidence may still be saved after cancellation, but the cancellation intent takes priority on every subsequent pass. SQL requires the saved sanitation receipt before a stop effect and a confirmed matching stop before a snapshot effect.

Without verifier ports, the controller ends at `verification_required`. Configured ports prepare a build-owned bootstrap, create its verifier IP/server, enroll through `/image/enroll` and persist a healthy distinct runtime result. Repeated passes after verification create no resources. It does not sign or promote a release and is not exposed as a live CLI command. Full abort works at every implemented stage, including after snapshot creation; unknown creates hold access and reservations until reconciled. The protocol fixture models server/IP/firewall attachments, while `smoke:builder` separately drives a real local VM through the durable controller. That smoke exercises lost install response recovery on a new database connection, sanitation intent ordering, stopped-source cloning and terminal cleanup. Provider observations remain a fixture, not Hetzner proof.

Verification is platform-owned. Reuse guest proof and certificate-validation functions; do not fabricate a customer allocation just to satisfy the existing enrollment tables. The verifier needs a distinct build-owned bootstrap/enrollment record and an explicitly configured reachable HTTPS endpoint. The implementation and current verification scope are in [platform image verification](image-verifier.md). Retained publication remains separate.

## Types and module ownership

- `packages/contracts/src/image-inputs.ts` owns validated inventories and artifact pins. `guest.ts` owns the format 2 manifest.
- `packages/images` owns public input inspection, canonical digest construction and release signing/verification. Filesystem and crypto code stay out of contracts.
- `packages/db` owns sibling `image_builds`, `image_build_effects`, `image_build_resources` and `image_builder_work` tables. No customer/account/allocation foreign keys. Unique provider/kind/resource identity prevents cross-build adoption; unique build/effect key prevents a second create intent for a role, even after rejection. Migration 0009 preserves admission, commands, receipts, resolutions and resource identities. A shared provider-identity lock prevents customer and operator journals from claiming the same resource concurrently.
- `apps/control/src/image-release-plan.ts` chooses a discriminated next step from one consistent SQL snapshot. `advance-image-build.ts` dispatches that step to the separately locked provider, builder or cleanup executor. The outer planner never holds a build lock while calling another executor. Phase-specific evidence belongs inside the phase variant, not nullable fields beside an enum. Cleanup is a separate intent that can only reconcile or delete.
- `apps/control/src/image-effect-journal.ts` commits provider intent before submission, reconciles existing intents, and retains immutable outcomes. `image-builds.ts` owns admission/inspection/cancellation; `image-budget.ts` owns gross price and aggregate allowance checks; `image-resources.ts` owns provider identities and observations; `image-effect-policy.ts` checks dependencies; `image-cleanup.ts` selects one owned deletion. `image-access.ts` owns operator key files and `image-renderer.ts` renders exact prepared builder boot data. Commands carry secret references, never raw user-data. `packages/remote/src/image-builder.ts` owns bounded SSH/SFTP installation; platform verifier enrollment and runtime modules share the subject-bound PKI and SSH reads.
- `packages/hetzner/src/image-release.ts` implements image/access HTTP transport using the existing fixed-origin, no-redirect, bounded request layer. `image-resources.ts` validates provider observations. The transport receives the persisted effect UUID and calls its boot renderer before sending an exact server request. It does not decide ownership, prices or retry policy. The operator CLI has no live advancement command yet.

Resource kinds are server, primary IP, SSH key, firewall and snapshot. Roles distinguish builder/verifier and their addresses. Each create request has exact build, role and persisted effect UUID labels. `imageEffectLabels` derives that set for submission, discovery, observations, final matching, dependency checks and deletion policy. Migration0012 rejects new observations with missing or different effect IDs. A receipt with incorrect current labels remains recorded but unverified; it cannot authorize deletion. Full 64-hex digests remain in metadata because Hetzner label values allow only 63 characters. Reconciliation records every duplicate ID and blocks fresh creation. Cleanup deletes only identities proven owned by both recorded intent and current provider evidence.

Before a fresh access/IP/builder create, policy reads the exact pinned base image and requires an available, nondeprecated Ubuntu 24.04 system image with matching architecture and a disk that fits the admitted offer. The renderer receives the committed effect UUID, not a newly invented request identity. Rendering failure makes no server request. Requests attach only the recorded SSH key, management firewall and persistent IPv4, with no IPv6 or automatic volume mount.

Action lookups check the exact action ID and its target association. A snapshot action belongs to its source server; the separate image receipt records the new snapshot ID. Only a provider `404/not_found` means an action is missing or a resource is absent. Missing actions do not permit another create. An authoritative desired state can finish a stop/delete; if the target still needs that operation, an identical exact-ID retry retains the original accepted receipt. Migration 0011 permits that one-way supersession while retaining the existing create prohibition. A running action or failed lookup cannot authorize the retry. Unavailable snapshot metadata remains readable for ownership/cleanup; it cannot satisfy successful creation.

The decoder accepts both `unassigned/null` and the historical `server/null` Primary IP representation. The current OpenAPI enum still lists `server` while its description announces `unassigned` from August 2026. An `unassigned` address with a nonnull server ID is contradictory and rejected. These transport fixtures are grounded in the [official OpenAPI document](https://docs.hetzner.cloud/cloud.spec.json). They are not a live paid-resource proof.

## Spending and recovery

The read-only account check at 2026-09-07T02:15:47Z found no servers, IPs, snapshots, firewalls or SSH keys. CPX12 was available at USD 27,798 gross micro-units per hour including IPv4. Snapshot storage was USD 24,477 gross micro-units per GB-month. A conservative 40 GB full-month reservation is USD 979,080 micro-units. For a 90-minute deadline, reserve two billable hours for each of builder and verifier. Four VM/IP hours add 111,192, giving a USD 1.090272 conservative admission envelope before an explicit cap margin. These are observed prices, not current admission authority; refresh before any paid effect. [Saved account evidence](../research/hetzner-image-catalog-check-2026-09-07.json).

Admission persists separate gross VM/IP and monthly snapshot caps, currency, an absolute build deadline of at most 24 hours, and explicit snapshot retention of at most 30 days. It reserves both possible VM/IP pairs for the entire build window, rounding each lifetime upward to whole hours. The operator allowance sums full admitted caps across all builds that have not completed cleanup. Admission and fresh-create checks share transaction lock 78131026; per-build execution uses a separate session lock. Fresh prices must fit each original gross component, not merely the aggregate. Network refresh happens outside those transactions. Count powered-off machines. No type or region fallback. Full-abort cleanup continues after expiry and cannot rent replacement capacity. Known duplicate resources can be deleted, but their uncertain create keeps the reservation until the outcome can be established. Duplicate history remains significant even after one candidate disappears. An empty lookup cannot prove that an uncertain create will never appear. Prepared or unknown stop/delete effects may be retried against the identical resource ID after ownership is checked again. The old resolution points to its prepared replacement; a create can never use that transition. Accepted running actions continue waiting. Deleting the source makes an unresolved stop fail explicitly. SQL refuses cleanup completion while any effect is pending or any resource lacks an absence observation. The current cancel path aborts the whole build, including an unpublished retained snapshot; retention-aware successful publication cleanup is unfinished. A provider outage can prevent deletion and extend billing; preserve unresolved ownership and report it rather than claiming the deadline stopped charges.

Installation interruption before a receipt requires disposal or explicit recovery of the same builder. Never reinstall across partially mutated state by pretending it is fresh. Lost sanitation response with access removed cannot authorize snapshotting. A receipt plus confirmed stopped source is required. Snapshot creation with an unknown response searches exact labels; zero or multiple candidates remains unresolved. Bind snapshot architecture, source, size, protection and labels before deleting the builder. Retained release promotion is transactional and occurs only after verification and successful signature checks.

## Design comparison

All three candidates converged on a sibling operator journal. Parent scores by rubric criteria 1–6 were A: 3/5/5/2/3/4 = 22, B: 5/4/3/2/3/4 = 21, C: 2/5/4/1/3/5 = 20. The independent judge scored A 24, B 22 and C 22 and selected A. The parent initially favored B's authenticated first connection, then accepted A's clearer spending and ownership model after comparing the complete designs. [Judge rationale](../research/image-release-review.md).

Use A as the base. Graft B's acyclic input chain and injected disposable host key, correcting its plaintext journal contradiction. Graft C's pure planner, interruption matrix and transactional promotion. Reject A/C first-seen host-key trust, B's same-price fallback, C's manifest hash cycle and fake verifier allocation, and optional-field state bags in all three sketches. There were no dropouts. Runtime verification remains open.

## Implementation order

1. Full input provenance, content-addressed staging and tamper checks.
2. Authenticated release contracts and validation, then operator journal/constraints and interruption tests.
3. Narrow Hetzner transport, isolated builder access and resumable cleanup.
4. Platform verifier enrollment, real snapshot boot and signed release consumption.
5. Bounded inexpensive provider drill, cleanup and production activation only after remaining renewal/recovery prerequisites.
