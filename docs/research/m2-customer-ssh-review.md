# M2 customer SSH synthesis review

Reviewed 2026-09-07 against `m2-customer-access-grounding.md`, the arena rubric, and the current authority, lifecycle, image-release, queue, and guest contracts. This is an artifact/source review; implementation and live-provider proof do not yet exist.

## Verdict

The selected A-based design is a suitable implementation base. The client-generated 32-byte ticket, hash-only persistence, ticket-file `ProxyCommand`, stable allocation principal, queued issuance, one CA submission per session, and monotonic 15-second authority horizon resolve the main arena objections. The design should not be treated as implementation-ready until the points below are made normative.

## Required corrections

1. **Make every issuance path durably terminal.** `AccessIssuance.unavailable` lacks outcomes for admission deadline expiry and a definite signer/provider failure. Add explicit bounded reasons (at least `deadline_exceeded`, `signing_failed`, and the existing uncertainty/authority/target reasons), and define which are retryable only by creating a new session. A retried Graphile task that reads `attempted` must never call the CA; it should recover a result only if the signer exposes a proven lookup key, otherwise persist `signing_unknown`. A pending task first run after the 90-second database deadline must persist `deadline_exceeded`. Give provider observation and CA calls abort deadlines capped by the original 90-second deadline. Queue retries must converge even after the request process and worker restart.

2. **Return the full grant authority horizon from the shared loader.** Current `loadPrincipal()` walks every ancestor but compares expiry with host `Date.now()` and returns only the leaf `Principal`. Move its persisted validity test to PostgreSQL time and return, or otherwise expose from the same validated walk, the earliest ancestry expiry. Admission, issuance finalization, claim, batch checks, grant issuance, and lifecycle callers must use this shared database-time decision. Do not recompute the SSH lease from the leaf expiry. Tests need an unexpired leaf under an expired parent and a host-clock skew case.

3. **Specify one lock order, including the existing global lock.** Access admission/finalization/claim should use `machine advisory -> global admission lock when that transaction uses shared ceilings -> account row -> machine/allocation/session rows`. Destroy already uses machine, global, then account. Grant revocation should keep its account lock and update the revoked subtree plus affected sessions without acquiring machine locks while holding the account lock; otherwise it creates the inverse `account -> machine` edge. The access final transaction then waits for the account lock and observes revocation. Define subtree selection and session closure in the same revocation transaction, including claimed sessions and descendants created before that transaction.

4. **Write the gateway claim as one concrete SQL authority contract.** After hash lookup, the locked claim must require: exact account/project/grant ancestry active at database time; session issued, unclaimed, and within ticket and hard-session deadlines; allocation still live and still attached to the machine; machine in the admitted running state/version; no cleanup intent or conflicting lifecycle operation; and exact live owned server/IP journal identities equal to the immutable target. It must atomically consume the ticket before TCP. The gateway must not perform provider discovery or accept any address/port from the caller.

5. **Persist the exact host identity pin returned to OpenSSH.** `OwnedSshTarget` currently records IDs, address, port, and alias but no host-CA key/fingerprint or pinned guest-host identity. Define which immutable signed release/allocation identity fields are stored with the issued session and returned in `known_hosts`. Bind the allocation-specific host principal and exact CA pin to the issuance fingerprint/final checks. SQL target checks prevent arbitrary forwarding; OpenSSH's exact alias/principal/CA check prevents a recycled address from impersonating the guest. Neither alone proves both properties.

6. **Add a signed customer-access capability, not a filename heuristic.** The current signed guest manifest has no capability field, and `requireCustomerImage()` only infers renewal support from two input paths. Extend the immutable manifest/release evidence with a versioned capability that represents the complete boundary: `agent-customer`, its sudo policy, sshd restrictions, stable allocation-principal admission, and the intended firewall/runtime behavior. Verify that capability in image verification, allocation pinning, and access admission. Existing retained M1 images must remain unsupported; a new verified image is required.

7. **Fix total time and idempotency semantics.** Persist all absolute deadlines from one admission-time PostgreSQL timestamp. Ticket expiry is `min(issued_at + 60s, admission + 90s, ancestry expiry)`; certificate validity and the hard connection lease must also be capped by the ancestry horizon. Queue delay must consume the 90-second issuance budget and never move any deadline. The POST idempotency fingerprint must include canonical machine ID, canonical public key, ticket hash, and all authority-changing options; same key/same body returns the original session in every state, while changed input conflicts. Capacity/rate queries must count pending, attempted/unknown, and issued-unclaimed reservations by database time, and the idempotent replay lookup must occur before those limits.

8. **Define GET/wait and live-failure bounds precisely.** State who may read a session after its issuing grant is revoked (for example, an otherwise authorized account ancestor) without weakening creation authority. The SDK wait deadline must be caller-bounded and no later than the session issuance deadline. At claim, initialize the monotonic hard deadline from database-reported remaining ancestry/session lifetime. Each periodic query gets its own timeout and the 15-second deadline starts when the query begins; failure or delay cannot extend it. Notifications remain acceleration only.

9. **Make the gateway's database privilege boundary explicit before implementation.** “Reads the database” is not a low-privilege boundary if the process inherits the control service's owner credentials: those credentials could mutate grants, resource journals, or other tenant state even though the gateway has no CA/provider files. Prefer a dedicated PostgreSQL role that can select only the authority projection it needs and can execute narrowly guarded claim, close, and batch-check functions; deny direct writes to grants, machines, allocations, provider journals, and certificate attempts. Provision that role outside gateway startup and make startup fail if its effective privileges exceed the expected allowlist. A narrow mutually authenticated gateway-to-control RPC is a valid simpler alternative if it keeps one authority implementation and supplies the same atomic claim/close semantics and 15-second fail-closed bound. Do not duplicate subtly different grant-chain SQL in two processes or present control-owner DB access as least privilege.

## Proof gates

Before claiming this slice complete, tests should demonstrate atomic job enqueue with rollback, replay before and after worker completion, worker crash in `pending` and immediately after persisting `attempted`, deadline expiry without CA submission, one total CA call under concurrent jobs, parent expiry/revocation races, destroy versus claim/finalization, SQL rejection of altered target/resource/CA pins, capability rejection for M1 images, claimed-ticket restart behavior, and monotonic closure under DB delay and wall-clock rollback. Native proof must retain distinct customer/probe credentials and show direct port-22 bypass rejected while the ticket-file proxy succeeds.

## Final addendum after correction

The revised `docs/architecture/customer-ssh.md` addresses all nine findings above. It now defines complete bounded issuance outcomes, database-time `loadAuthority()` with the earliest full-ancestry expiry, compatible lock ordering and transactional revoke closure, the exact claim predicate, immutable host CA/key/image pins, a signed and verified customer-SSH image capability, absolute total deadlines and replay semantics, explicit GET/wait behavior, and a gateway with no database credentials using one narrow control-owned authority implementation.

No material design contradiction remains before implementation. One implementation constraint should be tested explicitly: the worker's outer access-session advisory lock must stay on one dedicated PostgreSQL connection for the entire provider/CA pass even while row transactions are released. A pooled executor that returns that connection between phases would silently lose the exclusion guarantee. On crash or connection loss, the next worker must observe persisted `attempted`, terminalize it as `signing_unknown`, and make zero additional CA submissions. This is consistent with the corrected design and belongs in its required crash/concurrency proof.

The narrow gateway RPC is a cleaner privilege boundary than a database role here: the gateway holds only its hashed-policy bearer credential and public TLS trust, control retains all SQL, and claim/check/close share the same authority code. Verification still needs to prove that those routes are unavailable under ordinary customer credentials, bind check/close to the authenticated gateway plus exact claimed connection, reject redirects, and fail closed within the stated monotonic bound.
