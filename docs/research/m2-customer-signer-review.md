# M2 customer signer proposal review

Reviewed 2026-09-07 against the existing signer/workspace, SSH inspector, Smallstep template/setup, the native token-shape probe, and the selected customer SSH design. This is a proposal review. No customer signer, endpoint, gateway, or guest admission path is complete, and no paid provider proof is implied.

## Required implementation boundaries

1. **Make the template branch an exact, fail-closed namespace.** Branch only when `.Type` is `user` and `.Token.user.agentCloudAccess` has the expected purpose/version and complete fields. Render customer `keyId`, the single allocation principal, `source-address`, and `permit-pty` exclusively from that signed object. Do not merge request-provided principals/options/extensions. The other user branch must remain byte-for-byte equivalent to today's probe/runtime forced-command policy; host certificates must remain unchanged. Missing, malformed, partial, or customer-like claims must fall into the existing restricted path or be rejected, never into customer access.

2. **Prove token-to-key binding or document the OTT as the binding secret.** The observed `.Token.user.agentCloudAccess` placement proves custom signed fields reach the template, but it does not by itself show that Smallstep binds the one-time token to the public key submitted later to `/ssh/sign`. Include the canonical public-key fingerprint in the signed claim and use a template/request field that can compare it if Smallstep exposes the requested key. Add a negative native test that reuses/intercepts a freshly generated customer OTT with a different public key and proves rejection. If the CA template cannot inspect the requested key, state explicitly that possession of the unspent OTT authorizes any key for that narrowly scoped certificate, rely on Smallstep's one-use JTI plus the private in-memory/direct-TLS handling, and preserve the post-response exact-key inspection. Do not claim cryptographic key binding without that test.

3. **Keep the OTT out of argv, disk, logs, and errors.** Reuse one owner-only workspace helper for the root and provisioner-password files. `step ca token --ssh --set-file <claim-file>` may receive only nonsecret paths/subjects in argv; capture bounded stdout in memory, validate/trim exactly one token, and send it once in the JSON body. The direct HTTPS client must use the configured CA URL and pinned TLS root, reject redirects, cap request/response sizes, apply an abort deadline inherited from the session issuance deadline, and discard response/error bodies without logging the OTT. Cleanup must run on success, rejection, timeout, and cancellation.

4. **Inspect the customer certificate with a distinct policy.** Extend the inspector with a discriminated customer case rather than weakening probe/runtime expectations. Require user type, exact submitted Ed25519 key fingerprint, configured SSH user-CA fingerprint, exact audit key ID, exactly one allocation principal, exactly `source-address` as a critical option, exactly `permit-pty` as an extension, and no other option/extension. Verify the native Step JSON representation of empty extension values and CIDR serialization before encoding assumptions. Canonicalize/deduplicate/sort CIDRs once so the signed claim, template output, inspector, firewall policy, and stored session agree.

5. **Treat absolute validity as authority, not a requested hint.** Reject before token generation when `hardDeadline <= checkedAt`. Request `validAfter = checkedAt - 60s` and `validBefore = min(checkedAt + 240s, hardDeadline)`. This yields at most five minutes total certificate validity and at least Smallstep's one-minute minimum whenever positive authority remains. Define timestamp precision/rounding and inspect the returned absolute `ValidAfter`/`ValidBefore` so the CA cannot widen either bound; the current `inspectValidity` only checks a relative maximum around host `startedAt` and is insufficient for this DB-clock policy. Persist the inspector's actual expiry, which must equal or precede the requested hard bound.

6. **Preserve the single-attempt boundary above the signer.** The signer performs exactly one token generation and one `/ssh/sign` POST per invocation. It must not retry an ambiguous POST, refresh the OTT, or hide transport uncertainty behind a helper retry. Definite pre-submit failures may remain retryable while the session is pending; any failure after submission begins is an uncertain CA result for the access worker unless the protocol supplies a proven lookup receipt. The already-designed access-session advisory lock and immutable attempt receipt remain the owning durability boundary.

## Signature-validation judgment

The existing inspector parses native Step output and checks the embedded signing-key fingerprint and certificate policy; it does not independently verify the SSH certificate signature. Pinned TLS authenticates the CA service that returned the certificate, and native OpenSSH later verifies the signature against the pinned user CA. Under the repository's current trusted-CA-service boundary, a second in-process signature verifier is not a material authorization requirement: an invalid response fails closed at OpenSSH, while a malicious CA service already possesses the signing key. Native SSH proof must include successful customer authentication and rejection under the wrong CA/key/principal/source.

Describe this honestly as an authenticated CA response with exact structural/policy inspection, followed by native OpenSSH signature enforcement. Do not call `step ssh inspect` independent signature verification. If the product requires “issued” to mean cryptographically usable before publication, add an independent OpenSSH certificate signature verifier or a bounded verifier handshake; that improves availability/error classification rather than the stated trust boundary.

## Proof expected

Use the pinned Step0.30.6/step-ca0.30.2 fixture to prove exact claim placement, customer/probe/runtime/host branch separation, altered or missing claim rejection, public-key substitution behavior, CIDR ordering, absolute near-expiry validity, CA minimum-duration boundary, no extra SSH permissions, no OTT in argv/files/logs, one POST under lost response, and complete workspace cleanup. A native sshd test should accept the customer certificate only for `agent-customer`, the allocation principal, pinned CA, and an allowed source, while rejecting direct/wrong-source access and retaining the existing forced-command probe/runtime behavior.

Subject to these points, extending the current signer and sharing its private workspace is preferable to a parallel CA client or provisioner. It preserves the established operator CA and keeps customer policy as a narrow signed-template branch.
