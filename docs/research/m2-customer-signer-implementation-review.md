# M2 customer signer implementation review

Reviewed 2026-09-07 from the isolated `customer-ssh` worktree. This is a source and supplied-artifact review. I did not inspect private CA files, raw CA logs, or generated tokens, and did not operate a CA or VM.

## Findings

1. **P1 — preserve whether failure happened before CA submission.** `createCustomerSshSigner.sign` catches every exception and returns `unknown`, including an already-aborted signal, workspace creation/write failure, Step token-generation failure, and request construction/TLS setup failure before `call.end(body)` submits anything. The design distinguishes definite pre-submit failure from an ambiguous submitted request, and storage already has `signing_failed` as distinct from `signing_unknown`. Return a definite failure for errors known to precede submission and reserve `unknown` for failures once submission might have occurred. The transport should own an explicit phase marker set immediately before the single `end(body)` call; avoid inferring submission from error classes. This does not permit another CA call in the same persisted attempt. It gives the worker an honest terminal outcome and keeps “unknown” provenance accurate.

2. **P2 — inspection does not independently validate the SSH signature.** `step ssh inspect` plus `inspectCustomerSsh` verifies the embedded key, advertised signing-key fingerprint, key ID, principal, options, extensions, and exact validity. It does not cryptographically verify that the certificate signature was made by the pinned SSH user CA. Pinned HTTPS authenticates the expected CA service, and the native OpenSSH acceptance test will prove that the fixture produced a usable signed certificate, so this is not a blocker under the documented trusted-CA-service boundary. Keep that boundary explicit. If the controller is intended to reject corrupt or incorrectly signed CA responses before persistence, add an SSH certificate signature verifier against `userCa`; checking the certificate's embedded signing-key field alone is insufficient.

3. **P2 — template lexical checks are defense in depth, not parity with stored policy.** Production claims pass the strict TypeScript schema, which supplies canonical IDs and CIDRs. The template's ID patterns permit misplaced hyphens, and its CIDR pattern accepts strings such as malformed IP text or prefixes above the address-family maximum. A party able to mint provisioner-signed custom claims can therefore pass values that `accessGatewaySchema` would reject. This does not widen normal production output because `customerSshClaim` validates the complete stored session first. Do not claim the template independently enforces the canonical contract profile. Tighten the template/native negative matrix if resistance to malformed provisioner-signed claims is a stated CA boundary.

## Verified implementation

- `customerSshClaim` parses the complete persisted session, requires the immutable attempted/unclaimed state, refuses an expired issue deadline or authority, sorts the stored gateway CIDRs, and caps `validBefore` at the earliest authority expiry, original hard deadline, or `checkedAt + 240s`. The 60-second backdate yields no more than five minutes of total certificate validity.
- The token owns all seven customer policy fields. The customer template requires the customer branch, exact token/request key ID and principal, one principal, Ed25519 request type, exact marshaled request key bytes, signed sources, and signed absolute validity. Unsigned request options are not copied. The output grants only `permit-pty` and the `source-address` critical option. The existing host/probe/runtime branch remains unchanged.
- The OTT is produced in bounded subprocess stdout, never placed in argv or a file, and is sent in one bounded HTTPS POST to `/ssh/sign`. TLS uses the configured root, redirects are not followed, response size is capped, and all workspace files are removed in `finally`. The shared tooling retains the existing host/probe/runtime/TLS signing behavior and continues to place only trust and the provisioner password in an owner-only temporary workspace.
- A successful response is strict-parsed, converted to an OpenSSH certificate, and checked for exact policy. Rejected 400/401/403 responses are separated from transport/parse uncertainty. The supplied native transport artifact reports one POST for lost response, rejection, redirect, oversize, truncation, and cancellation; only the lost-response case followed real CA issuance. The supplied fresh-CA smoke also reports key substitution and malformed/unsigned claim rejection, immutable request policy, near-expiry validity, legacy credential compatibility, and absence of token logging.

## Follow-up review of corrections

The later isolated-worktree correction resolves finding 1. The signer now keeps an invocation-local `submitted` marker. It checks cancellation before constructing the request and again before submission, and changes the marker immediately before the sole `call.end(body)`. Failures before that boundary return `failed`; errors at or after it conservatively return `unknown`. Marking immediately before `end` is intentionally conservative if `end` itself throws: it can overstate uncertainty but cannot falsely authorize a retry after possible submission. The supplied native TLS proxy test reports that a broken token binary returns `failed` with zero POSTs, while every submitted fault still makes exactly one POST. Worker integration must map `failed` to the durable `signing_failed` terminal state and must never interpret it as permission for another call under the same immutable attempt.

The template now uses canonical hyphen-positioned UUID shapes for the session, grant, machine, and allocation identifiers and rejects duplicate signed sources. This resolves the concrete ID and duplication portions of finding 3. Full IP-family/prefix validation remains in `accessSessionRecordSchema`/`accessGatewaySchema`; the template's source regex remains deliberately lexical defense in depth. That is acceptable for the current controller-owned provisioner boundary once the architecture says so explicitly. Until that wording lands, the earlier warning against claiming independent template/contract parity remains open as documentation only.

The supplied second native SSH artifact materially strengthens finding 2's evidence boundary. A real sshd accepted command and PTY sessions for the exact customer key, user, allocation principal, source policy, and pinned host CA, while rejecting a bit-flipped certificate signature, wrong private key, wrong user, disallowed source, foreign allocation principal, port forwarding, and wrong host CA. The existing probe certificate retained its forced command on the same server. This proves that native OpenSSH validates the fixture certificate signature and enforces the emitted policy; it does not make `inspectCustomerSsh` itself a cryptographic verifier. The trusted pinned-TLS CA response remains the production signer boundary unless independent verification is later added.

Disabling `PerSourcePenalties` after rapid deliberate authentication failures is a fixture-stability choice, not a customer permission. The customer profile still disables forwarding and exercises the relevant certificate, principal, user, host-trust, and source restrictions. The fixture-only private NAT CIDRs prove source matching across Docker's observed host path; they do not validate an operator's real gateway egress CIDRs, firewall, image manifest, or provider network.

No production signer/template blocker remains in this bounded re-review. Final workspace-hygiene and rerun evidence were still in progress when reviewed. Worker, database finalization, API/SDK, gateway, access-capable image, and provider-network proof remain outside this checkpoint.
