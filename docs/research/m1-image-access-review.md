## Reviewed guarantees

### Secret storage and prepared-effect rendering

- `apps/control/src/image-access.ts` creates independent Ed25519 management and disposable host keys in owner-only per-build directories. It fsyncs all files and the staging directory before atomic publication, fsyncs the parent afterward, refuses incomplete/cross-intent reuse, reads secrets with `O_NOFOLLOW` plus owner/mode/size checks, and derives both public keys again from the exact private bytes returned to the caller. SQL receives public keys and a random secret reference; neither private key enters the admission or effect command.
- Concurrent prepare calls converge on one published directory. An existing incomplete directory blocks replacement rather than rotating identity. Recovery binds build UUID, manifest digest, management address, public keys and secret reference to the admission and reports a redacted failure.
- `apps/control/src/image-renderer.ts` accepts only the exact persisted create-server command while its effect is still prepared/pending and the build remains running and unexpired. It shares `checkImageBuilderIntent` with provider policy, requires confirmed dependency receipts, recovers the original keys, then rechecks build state, deadline and effect state before returning user-data. The caller’s build lock is the serialization boundary around rendering and provider submission.
- Cloud-init creates a dedicated `agent-cloud-build` account, injects the management public key and disposable host private key, disables root/password/ambient metadata keys, restricts SSH users, and validates sudoers and sshd configuration. `/run/agent-cloud-builder.json` binds build, effect and manifest. The management private key is never sent to the VM; the host private key is deliberately materialized only in provider user-data for this exact prepared attempt and is removed before snapshotting.

### First SSH, upload and installation recovery

- `packages/remote/src/ssh-files.ts` creates isolated temporary identity and known-hosts files and invokes OpenSSH with `-F /dev/null`, strict host checking, the pre-generated raw host key, one explicit identity, no agent, no forwarding, no proxy/jump/local command, public-key-only authentication and bounded liveness options. The first connection is therefore authenticated before any upload rather than learned by TOFU. The shared wrapper preserves the existing probe’s separate user, certificate and host-CA capability.
- The builder transport accepts only a validated IPv4 target and fixed builder account. Remote execution uses `execFile`, fixed SSH options, fixed `/usr/bin/sudo -- /bin/sh -c`, shell-quotes every positional value, and checks root, Ubuntu 24.04, amd64, completed cloud-init, the exact boot-record digest, ownership/modes and absence of symlink substitutions before interpreting state.
- Upload revalidates the complete local source and admitted checksum digest, refuses replacement after installation starts, recreates a fixed staging tree, and transfers only schema-bounded manifest paths plus derived metadata through SFTP. Before uploaded Node, guestctl or installer code runs, the remote base system validates the independently pinned `SHA256SUMS` digest, complete tree and file bytes through the existing trusted preflight.
- Installation creates a root-owned temporary copy of the exact boot record and atomically hard-links it as `install-started` before invoking the installer. Concurrent requests cannot both acquire that link. Once it exists, retries do not run the installer again: they return `started`, or recover and validate the durable `/usr/lib/agent-cloud/image-build.json` receipt. A lost successful SSH response is recoverable; a partial install remains durably `started` and requires disposal/recovery rather than another apt/install pass. SSH timeout is reported as unknown reachability, not proof that the remote process stopped.

### Sanitation

- Sanitation requires a completed install receipt bound to the boot build and manifest. It calls only the installed `guestctl prepare-image` capability and validates the returned sanitation receipt independently.
- Guest sanitation removes the builder sudo rule, sshd drop-in, installation marker/state, boot binding, staged inputs, system host keys, builder home contents, cloud-init state, logs, machine identity and generated Docker/containerd state. Builder access is removed at the end, so a lost receipt after that boundary cannot authorize snapshotting; the disposable source must remain unresolved for out-of-band recovery or deletion.
- Builder management is kept separate from the read-only `agent-probe` path. Refactoring common SSH file/options setup did not grant probe commands or credentials to the builder and retained the probe’s certificate-based trust rules.

## Native-discovered corrections

The three failures reported before active smoke `63643` exposed fixture and environment assumptions rather than weakening the recovery design. Their current fixes are behaviorally sound:

- Cloud-init 26.1 rejects an empty `ssh_genkeytypes`. The builder renderer now omits that option because its nonempty `ssh_keys` map supplies the exact pre-generated Ed25519 pair. The customer renderer uses an explicit empty `ssh_keys` map, which takes cloud-init's key-map-present branch and leaves first-boot host identity generation to guestctl as designed. Both set host-key publication off. The fixture runs `cloud-init schema` on the exact user-data before reboot, so this class of invalid configuration now fails before the smoke changes boot state.
- Growpart and root-filesystem resize are disabled only in OrbStack fixture datasource configuration, where the platform cannot perform the operation. Production user-data retains cloud-init's normal provider disk growth. The comments and placement make the fixture-only scope clear.
- The SFTP staging command now resolves `agent-cloud-build` through `id -g` and passes the numeric GID to `install`. This avoids assuming the primary group name equals the username while keeping ownership tied to the authenticated builder account. The value comes from the trusted base-system identity database before uploaded code runs.
- The installer now invokes the newly installed Node, Caddy and Step binaries by their exact `/usr/local/bin` paths. The trusted remote wrapper deliberately supplies only the base-system PATH; absolute invocation preserves that restriction and avoids relying on login-shell or sudo PATH behavior. The remaining installer commands are base-system paths available through the restricted PATH or already use absolute paths.

These changes address the observed failures without adding fallback identity, relaxing SSH trust, retrying a partial installation or changing production disk policy. Native smoke `63643` subsequently passed the full SSH/install/sanitation/clone path; the final evidence is audited below.

## Attention for lifecycle integration

The access store currently exposes only `prepare` and `recover`; `pnpm image:build cancel` changes journal state but does not erase local per-build private keys. Retention is necessary while an uncertain builder VM or temporary cleanup effect may still require authenticated recovery, so erasing at cancel time would be unsafe. The eventual runner should add an idempotent, owner-checked terminal deletion after the builder and its temporary access/IP/firewall/key resources are authoritatively absent and no SSH recovery remains. A deliberately retained sanitized snapshot does not need deletion merely to erase obsolete builder keys: it no longer contains that access, and its ownership/retention continues separately in the provider journal. Until this step is wired, operator-local disposable management and host keys can remain on disk after ordinary builds. This is unfinished lifecycle wiring rather than a defect in the current checkpoint.

The renderer’s dependency check uses confirmed SQL observations, while `runImageEffect` performs the live provider dependency check immediately before committing the server effect and invokes rendering under the serialized submission path. Preserve that sequencing when the live advancement runner is added; exposing the renderer independently of the journal lock would weaken the cancellation and dependency race argument.
